# birdwatch-api

The backend of **Birdwatch**, the birding demo of Capture The Feature Flag. It is NestJS 11, with mock birders, species and sightings, and evaluates flags through the [Evaluator](../evaluator/README.md) with [`@ctff/nestjs`](../../libs/nestjs/README.md). Its website is [birdwatch-web](../birdwatch-web/README.md).

## Logging in

There are no accounts. A visitor picks one of the mock birders (Alice in CA, Bram in NL, Chiara in IT, Dev in CA, in [src/data/birders.ts](src/data/birders.ts)), and `POST /api/session` returns a session token for them: a JWT (HS256) signed with a fixed dev key, with the birder's user ID as `sub`, their `name` and their `country`. It lasts 12 hours. The key is no secret: this is a fake login, for the demo only.

Every other `/api` route needs `Authorization: Bearer <token>`, and answers `401` without a valid one ([src/session/auth.guard.ts](src/session/auth.guard.ts), registered for the whole app). `BirderContextResolver` ([src/session/birder-context.resolver.ts](src/session/birder-context.resolver.ts)) is the app's `CtffContextResolver`: it evaluates flags for the context `{ user_id: <sub>, country: <country> }` read from the token.

## API

| Route                 | What it does                                                                                                      |
| :-------------------- | :---------------------------------------------------------------------------------------------------------------- |
| `GET /api/birders`    | The birders a visitor can log in as (no token needed)                                                             |
| `POST /api/session`   | Logs in as `{ "birderId": "alice" }`: `{ token, expiresInSeconds, birder }`, or `404` for an unknown birder       |
| `GET /api/sightings`  | The sighting feed, most recently observed first, with the birder and their flags                                  |
| `POST /api/sightings` | Logs a sighting (`speciesId`, `location`, `count`, optional `notes` and `observedAt`), behind `new-sighting-form` |
| `GET /api/species`    | Every species, with the birder and their flags                                                                    |
| `GET /health/live`    | Liveness                                                                                                          |
| `GET /health/ready`   | Readiness: the API only listens once it has its SDK key, so once it answers it is ready                           |

The response shapes, the limits of a new sighting and the demo's flag keys live in [`@ctff/birdwatch-contract`](../../libs/birdwatch-contract/README.md), which the website uses too. The flags come as the SDK's `AllFlags` (see [`allFlags`](../../libs/sdk/README.md#allflags)), loaded with `@Flags()`, so one request makes one Evaluator call. When the Evaluator can't be asked, `values` is empty and the website falls back to `false`.

`POST /api/sightings` is guarded by `@RequireFlag('new-sighting-form')`: while the kill switch serves `false` (or the Evaluator is unreachable), it answers `404`, as if the endpoint didn't exist. A sighting that doesn't check out gets `400`, with a message per field in `fields` ([src/sightings/new-sighting.ts](src/sightings/new-sighting.ts)). Logged sightings are kept in memory, up to 500: a restart, or another replica, shows the mock sightings alone.

## Configuration

All configuration comes from environment variables:

| Variable           | Default       | Meaning                                                                       |
| :----------------- | :------------ | :---------------------------------------------------------------------------- |
| `EVALUATOR_URL`    | required      | The Evaluator the SDK asks for flags                                          |
| `CTFF_SDK_KEY`     | none          | The SDK key of the environment to evaluate in                                 |
| `CORE_URL`         | none          | Without `CTFF_SDK_KEY`, the Core to look the SDK key up in                    |
| `CTFF_PROJECT`     | `birdwatch`   | The project whose environment's SDK key is looked up                          |
| `CTFF_ENVIRONMENT` | `development` | The environment whose SDK key is looked up                                    |
| `CTFF_TIMEOUT_MS`  | `500`         | How long the SDK waits for the Evaluator before falling back                  |
| `SESSION_SECRET`   | a dev key     | The key session tokens are signed with                                        |
| `PORT`             | `3000`        | HTTP port                                                                     |
| `HOST`             | `0.0.0.0`     | Interface to listen on                                                        |
| `LOG_LEVEL`        | `info`        | pino log level; logs are JSON lines on stdout, without `Authorization` header |

SDK keys are generated by Core, so the demo can't know them in advance. Unless `CTFF_SDK_KEY` is set, the API asks Core for the environment at startup (`GET /api/v1/projects/{project}/environments/{environment}`), and keeps asking every 2 seconds until Core has it, for instance while Core seeds it ([the demo seed](../core/README.md#the-demo-seed)) or Terraform creates it. It only starts listening once it has the key.

## Tests

Like the rest of Birdwatch, the API has no tests of its own beyond the end-to-end suite (S5), apart from unit tests of its pure helpers (session tokens, checking a new sighting): `pnpm nx run @ctff/birdwatch-api:test`. CI's compose job also runs [scripts/compose-smoke.ts](scripts/compose-smoke.ts) against `docker compose up`: Core seeded the demo, a birder logs in and logs a sighting, and switching the targeting of `new-sighting-form` off through Core hides "Log a sighting" on the website and makes the endpoint answer `404` within one poll interval.
